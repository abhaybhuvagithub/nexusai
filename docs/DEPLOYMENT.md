# NEXUS AI deployment guide

The Render Blueprint provisions a Next.js web service, FastAPI service, PostgreSQL database and Redis rate-limit store. Clerk provides sign-in; the API independently verifies signed bearer tokens.

## Clerk production setup

1. Create a production Clerk application.
2. Add the Render web origin to Clerk's allowed origins.
3. Set the web service's `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` in Render. Never expose the secret key in a `NEXT_PUBLIC_*` variable.
4. Create a Clerk JWT template named exactly `nexus-api`.
5. Configure its audience claim as `"aud": "nexus-api"` and use RS256 signing.
6. Copy the issuer claim from a token generated by this template into API `OIDC_ISSUER`; set `OIDC_AUDIENCE=nexus-api`.
7. Set `OIDC_JWKS_URL` to the matching Clerk JWKS endpoint, verified against the Clerk OpenID metadata.

The web app requests `getToken({ template: "nexus-api" })`; the API verifies signature, issuer, audience, expiry and subject. Use the production Clerk instance, not development credentials.

## Render deployment

1. Connect GitHub repository `abhaybhuvagithub/nexusai` to Render.
2. Choose **New → Blueprint** and select the repository.
3. Select branch `feat/production-hardening` for the first deployment review. After the release is approved, deploy from `main`.
4. Review the proposed resources: `nexusai-web`, `nexusai-api`, `nexusai-db` and `nexusai-cache`.
5. Enter prompted secrets in Render:
   - API: `OPENAI_API_KEY`, `OIDC_ISSUER`, `OIDC_JWKS_URL`
   - Web: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`
6. Verify the generated service hostnames. If they differ from the names in `render.yaml`, update web `NEXT_PUBLIC_NEXUS_API_URL` and API `CORS_ORIGINS` to the actual origins.
7. Confirm the API build completed `alembic upgrade head`. The health endpoints are:
   - `https://<api-host>/api/v1/health/live`
   - `https://<api-host>/api/v1/health/ready`
8. Sign up, create a conversation, send a model request, create a project, upload a sample document and verify usage counters.

Never put API keys, Clerk secrets or access tokens in source control, issues, pull requests or chat. Configure secrets only in provider dashboards.

## Current implemented behavior

- PostgreSQL stores conversations/messages, projects, knowledge text and usage events.
- Redis enforces a per-user rolling 60-second request counter on chat and agent calls.
- User-owned records are filtered by the verified OIDC subject.
- TXT, MD, CSV, JSON, LOG, PDF and DOCX uploads are text-extracted with a 5 MB file limit.
- Knowledge documents selected in chat are supplied as bounded context. This is currently explicit document context, not vector/semantic retrieval.
- Research produces model-assisted synthesis; it does not browse the web or provide verified external citations.
- Agent roles are specialist prompt workflows, not autonomous multi-step agents with arbitrary tool access.
- Usage counters are request/character telemetry, not token billing or a payment ledger.

## Operational release gates

Before broad public launch, add and verify: automated backup/restore drills, monitoring and paging, security and dependency scans, load testing, account export/deletion workflows, privacy policy/terms/retention controls, provider spend caps, admin support workflows and incident response. Confirm Clerk issuer/JWKS configuration and run end-to-end tests against the actual Render deployment.

The old GitHub Pages URL is a legacy static snapshot and is not the authenticated application. Render creates public web and API URLs only after the Blueprint is applied and services deploy successfully.
